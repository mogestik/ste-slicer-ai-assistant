# AI Assistant для STE Slicer

**Технолог внутри слайсера.** Плагин для STE Slicer (форк Cura 3.6 от Stereotech), который превращает задачу на обычном русском языке в готовый проект печати. Инженер описывает деталь, условия работы и нагрузку, прикладывает модель, фото или ТЗ — ассистент делает остальное и объясняет каждый шаг.

Обычный чат-ассистент даёт языковой модели кнопки слайсера и надеется, что она разберётся. У нас решения, от которых зависит деталь, принимает **расчёт**, а модель объясняет их человеку:

- **геометрия** — код сам находит ось вращения, сквозное отверстие и его диаметр, свесы каждой позы, выбирает 3D, 5D Spiral или 5D и ставит деталь на ось;
- **прочность** — нагрузка из ТЗ (изгиб, кручение, обороты, нагрузка на зуб) пересчитывается в индекс прочности для 3D и 5D с учётом анизотропии слоёв;
- **два сопла** — поддержки печатаются вторым материалом со второго экструдера;
- **материал** — подбирается из библиотеки Hybrid 530 по условиям эксплуатации, с честным «невыполнимо», если FDM не потянет;
- **результат** — нарезка, G-code и проект 3MF, которые ассистент сам перечитывает и сверяет со своими решениями.

Целевой принтер — Stereotech Hybrid 530 V5.2.4, слайсер — STE Slicer 7.10.12 под Windows. Все 41 инструмент ассистента доступны и внешним AI-агентам по протоколу MCP.

## Быстрый старт

**Установка в слайсер.**
1. Скопируйте папку `plugin/AIAssistant` в `%APPDATA%\steslicer\7.10\plugins\` и перезапустите STE Slicer.
2. Справа у края окна появится язычок «AI Assistant». Откройте панель, нажмите шестерёнку.
3. Укажите адрес OpenAI-совместимого API, ключ и модель, нажмите «Проверить подключение». Модель должна уметь вызывать инструменты (tools). Подойдёт и локальная LLM.

Для 5D-нарезки нужна активированная лицензия ATSS.

Руководство пользователя со справочником всех инструментов — [plugin/AIAssistant/docs/AI_Assistant_user_guide_ru.pdf](plugin/AIAssistant/docs/AI_Assistant_user_guide_ru.pdf), открывается кнопкой «?» в панели.

**Разработка без слайсера.** Нужен только Python 3.8+:

```bash
python -m unittest discover -s tests -t .
```

```bash
python devtools/run_standalone.py
```

Второй скрипт поднимает тот же сервер плагина с моком слайсера на `http://127.0.0.1:8765/`. Ключ LLM для стенда кладётся в `.env.local` в корне (`LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`); файл в `.gitignore`.

## Пример

> Копирный вал передающей звезды. Ролики из POM скользят по профилю без смазки, мойка щёлочью pH 11, точность профиля ±0,15 мм без ступенек. Вал работает на изгиб от роликов и кручение до 18 Н·м. Выбери режим печати сам. + `Ось вращения….STL`

Ассистент:
1. `analyze_model`: тело вращения, по оси сплошной материал → кандидат 5D с сердечником Ø6.
2. `recommend_material`: Enduse PA6 — износ, щёлочь, низкое трение.
3. `compare_print_strategies(loads=[shaft_bending, torsion])`:

   | Вариант | Индекс прочности | Изгиб | Кручение | Поддержки |
   |---|---|---|---|---|
   | 3D, ось вертикально | 0,68 | 0,55 — поперёк слоёв | 0,81 | да |
   | 3D, ось горизонтально | 0,96 | 1,00 | 0,93 | да, ступеньки на профиле |
   | **5D** | **1,00** | **1,00** | **1,00** | **нет** |

4. Выбирает 5D: стоя 3D теряет треть прочности на изгибе, лёжа — получает поддержки и ступеньки на рабочем профиле.
5. Ставит вал осью на ось стола, нарезает, сохраняет G-code и 3MF, проверяет их (`verify_project`: 100 %) и выдаёт карточку: параметры с источниками, строку «Прочность», статус каждого требования ТЗ.

## Как это работает

```
Панель QML ──HTTP──▶ http_server ──▶ SessionManager ──▶ LLM (Chat Completions + tools)
    ▲                                    │   ▲
    └──── long polling: события ◀────────┘   │ результаты инструментов
                                             ▼
                              реестр инструментов ──▶ адаптер слайсера ──callLater──▶ главный поток Qt
внешний агент ──MCP /mcp──▶ тот же реестр
```

1. Пользователь пишет в панели. Панель — QML внутри главного окна слайсера; с ядром плагина она общается через локальный HTTP API на `127.0.0.1`.
2. На каждое сообщение `SessionManager` запускает «ход» в отдельном потоке: отправляет модели историю, системный промпт и схемы инструментов.
3. Модель вызывает инструменты. Реестр проверяет и при необходимости чинит аргументы, выполняет обработчик и возвращает результат модели. Цикл повторяется, пока модель не ответит текстом.
4. Обработчики работают со слайсером только через адаптер. Всё, что трогает сцену и настройки, выполняется в главном потоке Qt через `callLater`; долгие операции (загрузка, нарезка, запись файлов) ждут результата в рабочем потоке.
5. Ход публикует события: текст ответа по мере генерации, вызовы инструментов, прогресс нарезки, итог. Панель забирает их long polling'ом и рисует.
6. В конце агент сохраняет G-code и 3MF, сам перечитывает их (`verify_project`) и только после этого выдаёт карточку с решением.

Типичная цепочка для нагруженной детали: `analyze_model` → `recommend_material` → `compare_print_strategies` → `set_print_mode` → `set_material` → `get_print_preset` → `select_profile` → `set_settings` → `load_model` → `suggest_orientation` → `rotate_object` / `move_object` → `start_slicing` → `export_gcode` → `save_project` → `verify_project`.

## Ключевые возможности

### Геометрия решает режим печати, а не языковая модель

Модуль `geometry` на чистом Python (без numpy) читает STL, OBJ и 3MF и ищет:
- **ось вращения** — по круглости сечений вдоль кандидатов в оси, с подгонкой окружностей;
- **сквозное осевое отверстие** и его диаметр — лучами вдоль оси; видит лыски, шпонки и ступени;
- **материал на оси** — сплошной вал, ступица или тонкая оболочка без опоры;
- **свесы каждой позы** — площадь, долю и необходимость поддержек.

По этим признакам он рекомендует 3D, 5D Spiral (Base Diameter = диаметр отверстия) или 5D (сердечник Ø6) и выдаёт готовые шаги поворота и центр для постановки детали на ось стола. Модель принимает решение по числам, а не «на глаз». Если отверстие больше прутка цанги, ассистент говорит, какую оснастку напечатать.

### Прочность под нагрузку из ТЗ

FDM-деталь слабее поперёк слоёв, поэтому важно, как слои лягут относительно напряжений. В 3D слои плоские, в 5D — цилиндры вокруг оси. Инструмент `compare_print_strategies` ([geometry/strength.py](plugin/AIAssistant/agent/geometry/strength.py)):

1. Принимает нагрузки, которые агент перевёл из ТЗ: `shaft_bending`, `torsion`, `axial_tension`, `centrifugal`, `hoop_pressure`, `radial_load`, `gear_tooth`, `custom`.
2. Раскладывает каждую на главные направления напряжения в осях детали (осевое, радиальное, окружное).
3. Для каждого варианта — лучших поз 3D, 5D Spiral и 5D — считает в 36 точках окружности угол θ между напряжением и слоем и прочность по критерию Цая–Хилла:

   `1/s(θ)² = cos⁴θ/X² + (1/S² − 1/X²)·cos²θ·sin²θ + sin⁴θ/Z²`

4. Выдаёт индекс 0…1, худшую нагрузку и поддержки каждого варианта.

Коэффициенты анизотропии зависят от класса материала из библиотеки H530:

| Класс | Поперёк слоёв, Z | Сдвиг, S |
|---|---|---|
| PLA, PETG, ABS, ASA, PC | 0,55 | 0,60 |
| С волокном (CF, GF) | 0,45 | 0,50 |
| TPU и эластомеры | 0,80 | 0,80 |

Правило выбора: разница индексов не меньше 0,15 — решает прочность; меньше — решает геометрия (поддержки, свесы). Если выбранный вариант проигрывает по прочности на 0,08 и больше, ассистент прямо пишет, чем платим. Режим, который назвал пользователь, главнее, но ассистент предупредит, если он заметно слабее.

Это **инженерная оценка** по типичным данным анизотропии FDM, а не МКЭ и не замена испытаниям; ассистент так и помечает её — «[оценка]».

Результаты на моделях кейса (`python devtools/strength_table.py`):

| Деталь | Нагрузки | 3D | 5D | Выбор |
|---|---|---|---|---|
| Шестерня | зуб, кручение | 0,83 | 0,81 | 3D — решает геометрия |
| Колесо конвейера | обод, кручение | 1,00 с поддержками | 0,90 | 5D Spiral, цена — радиальная прочность |
| Колесо насоса Wilo | обороты | 1,00 с поддержками | 0,83 | по прочности 3D; при «печать в 5D» — 5D с предупреждением |
| Крыльчатка | обороты | 1,00 | 0,86 | 3D |
| Вал Krones | изгиб, кручение | 0,68 стоя, 0,96 лёжа с поддержками | 1,00 | 5D |

Расчёт не подыгрывает 5D: для шестерни и крыльчатки он оставляет 3D.

### Два сопла Hybrid 530

Если пользователь просит, `set_support_material` печатает поддержки другим материалом со второго экструдера: ставит материал на экструдер 2, назначает экструдер поддержек, включает черновую башню и предупреждает о несовместимых парах (адгезия, температуры, растворимость). Работает в режиме 3D; проверено в STE Slicer.

### Подбор материала с честным «нет»

`recommend_material` подбирает материал из 32 позиций библиотеки Hybrid 530 по температуре, среде, гибкости, нагрузке и плотности. Для каждого требования ТЗ ассистент пишет «выполнимо», «с оговорками» или «невыполнимо» и почему. Если ни один доступный материал не закрывает ТЗ целиком, он так и говорит и называет нужные испытания.

### Партии на одном столе

На запросы вроде «партия из 15 фигурок» ассистент считает, сколько копий помещается на стол, размножает деталь (`duplicate_object`) и раскладывает копии; если все не помещаются — говорит, сколько нужно столов.

### Самопроверка результата

`verify_project` перечитывает сохранённый 3MF и G-code: режим, материал, профиль, изменённые настройки, положение модели, системы координат и оси 5D (G56, A, C). Расхождения агент исправляет до того, как показать итог.

## Архитектурные решения

**Один реестр инструментов для LLM и для MCP.** Инструмент описывается один раз: имя, описание, JSON-схема и обработчик. Из этого описания получаются и элемент `tools` для модели, и инструмент MCP. Ассистент в чате и внешний агент работают с одинаковым набором, а новый инструмент сразу доступен в обоих местах.

**Адаптер слайсера и мок с одним интерфейсом.** Обработчики не импортируют `UM`/`steslicer` — они вызывают методы адаптера. В слайсере это `QtSlicerAdapter`, на стенде и в тестах — `MockSlicerAdapter`. Мок проверяет правила потоков: метод «главного потока», вызванный не оттуда, падает. Так ошибки многопоточности ловятся тестами, а не зависанием слайсера.

**Строгие правила потоков.** Сцену и настройки трогаем только из главного потока Qt (через `callLater` и ожидание результата). Запись G-code и 3MF — наоборот, только из рабочего потока: писатели слайсера помечены `@call_on_qt_thread` и зависают при вызове из главного. Это правило мы нашли в исходниках слайсера, и вокруг него построен весь адаптер.

**Своя панель на QML вместо веб-интерфейса.** В сборке STE Slicer нет QtWebEngine, поэтому показать веб-страницу внутри окна нельзя. Панель нарисована на QML, встроена в главное окно справа, сужает 3D-вид под себя и забирает мышь, чтобы не крутилась сцена. С ядром она общается через тот же HTTP API, что и MCP-клиенты.

**Только стандартная библиотека Python 3.5.** В слайсере нет pip, поэтому клиент LLM (с потоком SSE, повторами и отменой), MCP-сервер, чтение STL/OBJ/3MF/DOCX, геометрия и расчёт прочности написаны на stdlib. Совместимость проверяется `vermin -t=3.5-`.

**Детерминированная база знаний.** Материалы Hybrid 530 с оценками свойств, пресеты под задачи и справочник 678 настроек слайсера лежат в `knowledge/`. Инструменты `recommend_material`, `get_print_preset`, `search_settings` отвечают одинаково на одинаковый вопрос. Справочник ещё и исправляет частые ошибки модели вроде `fill_density` → `infill_sparse_density`.

**Защита от слабостей недорогих моделей.** Ассистент рассчитан на недорогие модели (тестировали на Qwen flash):

- аргументы в блоке ```, с ведущими нулями, в стиле Python или закодированные дважды разбираются;
- одинаковые повторные вызовы отклоняет `LoopGuard`, а при цикле или лимите шагов агент просит итоговый текст;
- 19 редких инструментов не отправляются на каждом шаге: модель подключает их через `enable_tools`, а часть подключается заранее по словам из сообщения («партия», «второй экструдер», «профиль»…);
- фото отправляются один раз, старые результаты в истории сокращаются;
- история перед каждым запросом приводится к виду, который точно примет API.

**Промпт — это файл.** `prompts/system_ru.md` перечитывается на каждом ходу, поэтому поведение агента можно править без перезапуска слайсера.

## Чем мы гордимся

- **Работает в настоящем STE Slicer.** Полный цикл от запроса до G-code и проекта 3MF пройден на семи моделях кейса в STE Slicer 7.10.12, включая 5D-нарезку и поддержки вторым экструдером. Автоматическая проверка сохранённых проектов по нашему прочтению ТЗ — от 87 до 100 %.
- **Расчёт вместо догадки.** Режим, Base Diameter, постановка на ось и выбор 3D/5D под нагрузку считаются кодом. На семи моделях цепочка инструментов без LLM даёт 100 % совпадения с ожиданиями.
- **Разобрались в устройстве слайсера.** Нашли и обошли неочевидные вещи: у всех бэкендов нарезки один общий объект сигнала прогресса; писатели файлов зависают из главного потока; `setMaterialById` может молча поставить пустой материал; ось C в 5D G-code — накопленные градусы, а не миллиметры; Base Diameter молча вырезает часть модели. Всё это описано в комментариях адаптера.
- **Честные ответы.** «Невыполнимо» — тоже ответ. Ассистент не обещает того, чего пластик не выдержит, а оценку прочности помечает как оценку.
- **Ноль зависимостей.** Плагин ставится копированием одной папки и работает с любой OpenAI-совместимой LLM.
- **Проверяемость.** 234 теста. Стенд без слайсера. Поддельная LLM, которая нарочно присылает битые аргументы, обрывает поток и отвечает 429/500. Прогоны семи моделей без LLM и с настоящей LLM.

## Разработка

- Тесты: `python -m unittest discover -s tests -t .`. Часть тестов использует модели кейса из `models/` и без них пропускается.
- Цепочка по 7 моделям без LLM: `python devtools/pipeline_dryrun.py`.
- Расчёт прочности по 7 моделям: `python devtools/strength_table.py` (`--json` — полный вывод инструмента).
- Прогон с настоящей LLM: запустите стенд (или откройте чат в слайсере), затем `python devtools/live_run.py --url http://127.0.0.1:8765`. Пока идёт прогон, в чат не пишите — второй ход в той же сцене испортит результат.
- Проверка сохранённых файлов: `python devtools/check_3mf.py проект.3mf --target devtools/targets/01_gear.json`, `python devtools/check_gcode.py result.gcode`.
- MCP: `python devtools/mcp_smoke_test.py --url http://127.0.0.1:8765/mcp`.

Правила для кода плагина:

- только Python 3.5 и стандартная библиотека;
- сцену и настройки — только из главного потока Qt, запись файлов — только из рабочего;
- после изменений прогонять тесты, `pipeline_dryrun.py` и `mcp_smoke_test.py`.

## Что ещё не проверено в слайсере

- `compare_print_strategies` проверен на стенде с настоящей LLM (шестерня, Wilo, вал Krones) и в тестах; в STE Slicer, в том числе по объекту сцены, — ещё нет.
- `duplicate_object` (копии детали для партии) проверен только на моке слайсера и в тестах.
- Коэффициенты анизотропии — типичные для FDM, а не измеренные на филаментах Stereotech. Центробежная нагрузка учитывается по направлениям; расчёта на разрыв от оборотов нет, обороты идут только в текст.
